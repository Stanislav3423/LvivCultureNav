# ЛР3 — картки для дошки Trello «LvivCultureNav»

Ітерація **I3 «Рефакторинг»**. Колонки ті самі, що в ЛР1–ЛР2: **Backlog → To Do → In Progress → Testing → Done**.

**Мітки** (створіть, якщо їх ще немає на дошці):

| Мітка      | Колір (довільно) | Для чого               |
| ---------- | ---------------- | ---------------------- |
| `I3`       | фіолетовий       | усі картки ітерації    |
| `refactor` | синій            | усунення недоліку коду |
| `test`     | жовтий           | тестування             |
| `process`  | блакитний        | аналіз, планування     |
| `server`   | зелений          | серверна частина       |
| `client`   | помаранчевий     | клієнтська частина     |
| `shared`   | сірий            | спільний модуль типів  |

**Учасники:** першим на картку додайте відповідального, другим — пару.

**Як рухаються картки:** картка переходить у Testing, коли перетворення коду завершено, і в Done — коли
Яскульська Х. В. підтвердила, що проходять модульні, інтеграційні та E2E-тести.

### R-01. Валідатор подій і рядки помилок у формі

Мітки: I3, refactor, server, shared · Учасники: Володькін С. В., Баран В. Б.

**Недолік.** `validateEventInput` перевіряє дату, координати, медіа і переклади одним ланцюжком умов
(довга функція). Сервер повертає помилки англійськими рядками, а `EventForm` тримає їхні копії як ключі
перекладу — зміна тексту на сервері непомітно ламає переклад у формі («стрілянина дробом»).

**Спосіб усунення.** Декомпозиція умови: окрема перевірка на кожне поле. Перевірку меж Львова перенести до
`LVIV_BOUNDS` у спільний модуль. Тексти помилок оголосити один раз — `VALIDATION_ERRORS` у shared,
використовувати на сервері й у формі.

**Критерій готовності.** Тексти відповідей API не змінились; тести валідації проходять.

**Чекліст:**

- [ ] Окремі перевірки полів
- [ ] `isWithinLviv` у shared
- [ ] `VALIDATION_ERRORS` у shared, форма використовує константи
- [ ] Тести зелені

### R-02. HTTP-шар: дубльовані помилки та імпорт партнерів

Мітки: I3, refactor, server · Учасники: Володькін С. В., Яскульська Х. В.

**Недолік.** `res.status(...).json({ error })` повторено в усіх роутерах, id події розбирається по-різному
(дубльований код). Обробник `POST /api/partners/import` сам перевіряє події, шукає їх, створює або оновлює
і рахує результат — HTTP змішано з бізнес-логікою (довга функція, розбіжні зміни).

**Спосіб усунення.** Виділити функції `sendError`, `notFound`, `parseId`. Розділити імпорт на перевірку і
запис та перенести в сервіс `partnerImport.ts`; рядок `partner:<id>` замінити функцією `partnerSource`.

**Критерій готовності.** Коди й тексти відповідей API не змінились; є модульні тести сервісу імпорту.

**Чекліст:**

- [ ] `api/http.ts`: `sendError`, `notFound`, `parseId`
- [ ] Сервіс `partnerImport.ts`
- [ ] Модульні тести імпорту
- [ ] Інтеграційні тести API зелені

### R-03. Сервіс маршрутів має чотири обов'язки

Мітки: I3, refactor, server · Учасники: Володькін С. В., Баран В. Б.

**Недолік.** `createOsrmRouting` одночасно кешує маршрути, обмежує частоту запитів, звертається до OSRM і
перетворює відповідь (розбіжні зміни); формула округлення хвилин дублює `walkingMinutes`.

**Спосіб усунення.** Виділити кеш `RouteCache` і обмежувач частоти `createThrottle` в окремі модулі,
перетворення відповіді — у `toRouteResult`, округлення — у `minutesFromSeconds`.

**Критерій готовності.** Кеш, як і раніше, витісняє найстаріший запис і не зберігає запасну пряму лінію;
тести маршрутів проходять.

**Чекліст:**

- [ ] `RouteCache`
- [ ] `createThrottle`
- [ ] `toRouteResult`, `minutesFromSeconds`
- [ ] Модульні тести складових

### R-05. AdminPage: тристанний editingId, повтори обробки 401

Мітки: I3, refactor, client · Учасники: Баран В. Б., Володькін С. В.

**Недолік.** `editingId: number | null | undefined` кодує три стани форми (закрита, нова подія, редагування),
зрозумілі лише з коментаря (одержимість примітивами); завантаження списку з обробкою відповіді 401 повторено
тричі; ключ розіменовується через `key!`.

**Спосіб усунення.** Явний тип `FormState` (`closed | new | edit`); вхід, вихід, перезавантаження і обробку
401 винести в хук `useAdminSession`; розмітку — у компоненти `AdminHeader`, `AdminWorkspace`.

**Критерій готовності.** Регресійний тест «після створення події немає дубліката» проходить.

**Чекліст:**

- [ ] Тип `FormState`
- [ ] Хук `useAdminSession`
- [ ] Компоненти `AdminHeader`, `AdminWorkspace`
- [ ] Тести сторінки й E2E зелені

### R-07. TerminalPage: запит маршруту рядком «terminal:id»

Мітки: I3, refactor, client · Учасники: Баран В. Б., Яскульська Х. В.

**Недолік.** Запит маршруту кодується рядком `` `${terminal}:${id}` `` і розбирається `split(':')`
(одержимість примітивами); асинхронне завантаження подій і маршруту — прямо в компоненті; тип статусу
продубльовано в `EventList`.

**Спосіб усунення.** Замінити рядок об'єктом `{ terminal, eventId }`; завантаження винести в хуки
`useEvents` і `useRoute`; типи `LoadStatus`, `RouteState` — у `terminal/hooks.ts`.

**Критерій готовності.** Застаріла відповідь маршруту не показується; тести терміналу й E2E зелені.

**Чекліст:**

- [ ] Хуки `useEvents`, `useRoute`
- [ ] Типи в `terminal/hooks.ts`
- [ ] Тести хуків
